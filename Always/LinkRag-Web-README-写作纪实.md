# LinkRag Web README 写作纪实

> 记录我们这次是怎么把 LinkRag Web 的 README 从"还不错"打磨成"家族门面"的——过程、决策、踩坑与成果。配套方法论见 [README-写作指南.md](./README-写作指南.md)。

---

## 背景：一套系统，三个仓库

LinkRag 是一套企业级 RAG 系统，由三个仓库协作，各司其职：

| 仓库                              | 角色                       | README 风格 |
| --------------------------------- | -------------------------- | ----------- |
| `ql-link/LinkRag`（Python）       | RAG 引擎，整个系统的"门面" | 门面营销风  |
| `ql-link/LinkRag-Service`（Java） | 管理端后端                 | 工程朴实风  |
| `ql-link/LinkRag-Web`（本仓）     | 前端，用户直接接触的入口   | 待定        |

任务起点很朴素：**参考 Python 端和 Java 端 dev 分支的 README，想清楚 Web 端该怎么写。**

---

## 第一步：调研——先画出"风格光谱"

没有凭空动笔，而是先读懂两份参考样板。读完发现：三份 README 不是同一个风格，而是一条 **"从门面到工程"的光谱**。

- **Python 端**：居中 banner、一排 badges、在线体验大按钮、7 大功能每个配手绘图、关联仓库表、MIT。营销叙事，面向开源观众。
- **Java 端**：朴素标题、系统边界 ASCII 图、技术栈表、模块结构、快速开始、API 概览表、`Private Project`。工程实用，面向后端开发者。
- **Web 端（旧版）**：其实已经不差（功能特性、技术栈、本地开发都有），但缺三样**家族一致性**：① 关联仓库互链表 ② 系统边界图 ③ 头部门面（badges + 在线体验）。

> **关键认知**：Web 的最佳位置是"两头都沾"——用 Python 的门面头部（前端天生是视觉门面），套 Java 的务实骨架（它也是要被 clone、安装、联调的工程项目）。

---

## 第二步：定方向——三个决策不靠猜

涉及会显著改变成稿的分叉，**先问清楚再动手**。确认了三件事：

1. **风格基调**：门面头 + 工程骨架结合。
2. **产品命名**：统一用 `LinkRag`（远程仓库名 `LinkRag-Web`、域名 `linkrag.cn`、Python 门面都用这个，对外一致性最强）。原 Web README 混用 "ToLink · LinkRag Web"，要改。
3. **配图**：克制，暂不放界面截图。

> **为什么 Web 反而不该堆图**：Python 端配图多，是因为它讲的是"看不见的引擎"（解析、分片、三路召回这些抽象流程，不画图讲不清）。Web 讲的是"看得见的界面"，真正值得配的图其实只有界面截图本身。所以全篇只保留**一张架构图**就够。

---

## 第三步：找到 Web 的"灵魂"

每张好图、每份好 README 都有一个**一眼看懂的核心**。Web 的灵魂是：

> **一处收口、两路分叉** —— 所有请求收敛到一个统一的 API 客户端，再分成走向完全不同的两条线：带 `satoken` 走 Java 办常规业务（一问一答），凭临时通行证直连 Python 拉逐字流式问答（SSE）。

这是 Web 区别于"普通前端"的记忆点。**而且这个说法在源码里核实过**，不是照搬 Java README：

```
src/types/api.ts:420  // ── Recall (direct-to-Python SSE) ──
RecallSessionDTO.streamUrl   // Java 签发，前端凭它直连 Python
```

## 第五步：架构图——从"生图脚本"到 hero 图

Web 那张手绘架构图，是这么来的：

1. 用 `code-sketchnote-prompt` skill 生成一份 **"生图脚本"**（一份 Markdown 提示词文档，直接喂给文生图模型）。核心是把模块**蒸馏成图像模型能画的结构**：灵魂（一处收口两路分叉）+ 8 个节点 + 3 张旁注卡 + 箭头图例 + 关键标注。
2. 三条铁律保证手绘质感：**松散布局**（不画等宽泳道）、**控字**（每框只标题+一句话）、**大白话**（`satoken`→"对暗号的专用请求头"、recall session→"临时通行证"、SSE→"逐字涌动的小点"）。
3. 用户拿脚本出图后，把图作为 **hero 图放到 header**（badges + 在线体验之后），对齐 Python 端 header 结构。

> 一张总览 hero 图不算"堆图"，和"配图克制"不冲突——克制针对的是给每个功能配图、放界面截图。

## 第七步：提交——规范的代价

这一步踩了几个坑，也立了几条规矩：

- **commit 格式**：三仓统一规范在 Python 端 `docs/contributing.md §1.2`（它自述是"唯一规范文档"）——`<类型>(<范围>): <动作> <对象>`，主题 ≤70 字符。最终用了 `docs(readme): 重写 README 并补充英文版与架构图`。
- **不用 `git add .`**：逐个文件精确指定，避免夹带。
- **worktree 纪律**：当前就在 worktree 根，直接跑 git，不 `cd`、不碰 `.git`。
- **提交前先同步 dev**：这条最关键——给 Java 端也补英文版时，先 `fetch` 检查 dev，**发现 dev 上的 #130 已经把同样的事（门面+英文版+MIT+手绘图）做完并合并了**。我们的分支既重复又过时，及时废弃，避免了一次无用且冲突的 PR。

成果：Web 端 [PR #108](https://github.com/ql-link/LinkRag-Web/pull/108)（conventional commit，base = dev）。

## 沉淀下来的几条经验

1. **先调研再动笔** —— 画风格光谱，让定位有据，而不是凭感觉。
2. **找灵魂** —— 一句话能说清的核心，是 README 和配图的主线。
3. **配图克制** —— 只配"讲不清的"；结构比体积更有信息量。
4. **源码核实** —— 架构描述在代码里验证，不照搬别人的说法。
5. **提交前先同步 dev** —— 一次 `fetch` 省下一次重复劳动。
6. **决策不靠猜** —— 影响成稿的分叉（风格、命名、License）先问清楚。
7. **验证要有证据链** —— "图能显示"是验证出来的，不是声明出来的。
