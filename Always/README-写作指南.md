# README 写作指南

> 从 LinkRag Web 的实践中提炼的通用方法论。配套案例见 [LinkRag-Web-README-写作纪实.md](./LinkRag-Web-README-写作纪实.md)。

---

## 一、核心理念

README 是项目的门面。目标是让技术读者 **"秒懂这个项目值不值得关注"**——既有**工程诚意**（架构图、技术栈、真实功能细节），又有**产品吸引力**（用户视角的价值主张、截图、在线体验入口）。

两个极端都要避免：纯营销（华而不实，开发者不信任）、纯罗列（劝退，看不出价值）。

---

## 二、动笔前：调研与定位

**不要凭空写。** 先做三件事：

1. **读关联/同类项目的 README，画一条"风格光谱"**：从"门面营销风"到"工程朴实风"，找到自己该站的位置。
   - 面向开源观众/评估者 → 偏门面（banner、badges、在线体验、配图）。
   - 面向协作开发者 → 偏工程（系统边界、技术栈、快速开始、API）。
2. **确定读者**：C 端普通用户、企业团队、还是开发者？这决定**第一句话**怎么写。
3. **多仓项目找"家族约定"**：统一的命名、统一的关联仓库表、统一的 License、一致的配图风格。让人一眼看出是同一个项目的不同部分。

---

## 三、标准结构（章节顺序）

```
1. Header        标题 + tagline + 语言切换 + badges + 在线体验按钮 + hero 图
2. 是什么         一段定位 + 一段核心链路（末尾链到技术文档）
3. 功能特性       6–8 个，每个"痛点→实现→收益"
4. 系统边界       本仓在整个系统中的位置（多组件项目必备）
5. 技术栈         表格
6. 快速开始       前置条件 + 最少步骤跑起来
7. （目录/脚本/联调/部署/分支）  工程细节
8. 关联仓库       多仓互链表
9. 文档 / License
```

单仓项目可省略"系统边界""关联仓库"；没有在线部署则去掉在线体验按钮。

---

## 四、Header 的 GitHub 渲染铁律

这些是从踩坑里总结的，**必须遵守**：

- **`<div align="center">` 里只放 `# 标题` 和一句 tagline**。badges、图片放在 div **外面**，单独用 `<p align="center">` 包。
- **禁止用 `<table>` 做 header 排版**：GitHub 暗色模式会把 table 边框渲染出来，形成丑陋矩形框。
- **不要把 logo 内联进 `# 标题`**（`<img align>` 基线对不齐）。纯文字标题最干净。
- **在线体验按钮**单独一行，金色大按钮：
  ```html
  <p align="center">
    <a href="URL"
      ><img
        alt="在线体验 domain"
        src="https://img.shields.io/badge/在线体验-domain-c8a06a?style=for-the-badge&logo=googlechrome&logoColor=white"
    /></a>
  </p>
  ```
  颜色 `c8a06a`（暖金）、style `for-the-badge`（大号），不和其他 badge 混排。
- **hero 图**：`width="840"`；功能展示图 `width="680"`；截图 `width="880"`。
- **图片路径用相对路径** `./docs/assets/...`，并确保图片**已入库**。

## 五、文案风格

- **tagline 公式**：前半段用户价值，破折号后核心动作。
  > 人人可用的企业级 RAG 系统——把复杂文档，变成可以对话的知识。
- **首行禁忌**：不写"面向企业的…"。即使是企业级产品，受益方也是"每个人/任何人"，语气是"人人可用"而非"专供企业"。
- **功能描述**：用 `痛点 → 实现亮点 → 收益` 的结构，让读者感受到工程取舍背后的思考。避免"支持 xxx / 提供 xxx"式罗列。
  > **三路召回，各取所长**——没有哪种检索能包打天下。同时跑稠密向量、稀疏向量、BM25 三路，用 RRF 稳定融合……让"第三节那张表"也能被单独命中。

## 六、配图原则：克制

**图像的丰富来自结构，不是体积。**

- **只配"讲不清的"**：抽象流程（解析、分片、召回这些"看不见的"）值得配图；"看得见的界面"用截图。如果文字表格就能说清，别配图。
- **别给每个功能都堆图**：一份 README 通常一张 hero 总览图就够，最多关键流程几张。
- **功能图单列堆叠**，不要并排（并排后每张只剩 ~46% 宽，细节看不清）。
- **多仓项目配图风格家族一致**（同一套手绘/线条风格、同一个目录 `docs/assets/sketches/`）。
- **手绘架构图技巧**（若用文生图模型）：蒸馏成"灵魂 + 6–9 节点 + 2–3 旁注卡 + 箭头图例 + 少量数字"；布局措辞松散（避免"等宽泳道/网格对齐"，否则被画成流程图）；节点只写标题+一句话；**不用代码名**，全大白话（`afterCommit`→"数据库提交后"、`turn_id`→"本轮唯一标识"）。

---

## 七、讲清楚"你在系统中的位置"

多组件项目，必有一张 **系统边界图**（ASCII 或手绘），说明本仓和其他组件怎么协作、数据怎么流。

- 突出**本仓独有的亮点**（比如"前端凭短期 token 直连 Python 拉 SSE，绕过 Java"）。
- 架构描述要**在源码里核实**，不照搬别处的说法。

ASCII 示例：

```text
   ┌──────────┐  satoken·/api/v1   ┌──────────┐   签发 token   ┌──────────┐
   │  前端    │ ─────────────────▶ │  Java    │ ─────────────▶ │  Python  │
   │          │ ◀───── 业务数据 ── │  管理端  │                └────┬─────┘
   └────┬─────┘                    └──────────┘                     │
        └──────────── 召回 SSE · 前端凭 token 直连 ──────────────────┘
```

## 八、关联仓库表（多仓项目）

三仓互链，一眼看懂协作关系：

```markdown
| 仓库                 | 角色        |
| -------------------- | ----------- |
| [org/A](url)（本仓） | 核心服务：… |
| [org/B](url)         | 服务端：…   |
| [org/C](url)         | 前端：…     |
```

---

## 九、命名与 License

- **命名统一**：对齐远程仓库名、域名、其他端的叫法。一处混用（如 "ToLink · LinkRag"）会削弱专业感。
- **License**：README 里声明 + 仓库根放 `LICENSE` 文件（MIT 等需要版权署名：组织/公司名 + 年份）。多仓项目协议应一致。

---

## 十、双语版本

补 `README_EN.md` 时：

- **结构完全镜像**中文版，章节一一对应。
- **语言切换器互指**：中文版 `**简体中文** · [English](./README_EN.md)`，英文版 `[简体中文](./README.md) · **English**`。
- 技术术语**不翻译**（Embedding、Chunking、RRF、SSE、BM25…）。
- 中文破折号句式改用英文冒号或 em dash（`—`），避免翻译腔。

---

## 十一、提交规范（以 Conventional Commits 为例）

- 格式 `<类型>(<范围>): <动作> <对象>`，主题 ≤70 字符。类型：`feat`/`fix`/`refactor`/`docs`/`test`/`chore`/`perf`。
  > `docs(readme): 重写 README 并补充英文版与架构图`
- **精确暂存**，不用 `git add .`（避免夹带不相关改动）。
- **提交前先 `fetch` 同步目标分支**，确认没有别人已经做了同样的事——一次 fetch 能省下一次重复劳动。
- worktree 里直接跑 git，不 `cd`、不碰 `.git`。

---

## 十二、收尾检查清单

- [ ] `<div align="center">` 里没有图片、没有 `<table>`
- [ ] 在线体验按钮单独一行、颜色 `c8a06a`
- [ ] 功能图片单列堆叠，没有并排 `46%` 写法
- [ ] tagline 没有"面向企业的"措辞
- [ ] 图片路径相对可访问（`./docs/assets/...`）且**已入库**
- [ ] 命名全仓统一，无混用
- [ ] 多仓项目：关联仓库表 + 系统边界图齐全
- [ ] 有英文版则结构镜像、切换器互指
- [ ] 图片真的能显示（路径匹配 + 入库 + 渲染验证，而非"应该没问题"）
