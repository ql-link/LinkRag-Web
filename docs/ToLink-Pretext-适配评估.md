# ToLink-Web 对 `pretext` 的适配评估

## 1. 结论先行

`pretext` 值得关注，但不建议现在作为 `toLink-Web` 的通用基础设施立即引入。

更准确地说：

- 它不适合拿来做当前这轮首页、欢迎页的视觉升级
- 它适合未来用于“文本排版精度”和“长列表性能”这两个专项
- 在 ToLink 当前代码里，最可能的落点是聊天消息区、知识图谱节点文本、引用卡片/富文本片段

如果要排优先级，我的建议是：

1. 当前阶段不引入
2. 等聊天发送、流式响应、引用展示等核心能力补齐后，再做一次专项评估
3. 真正接入时，从局部场景试点，不要一上来全站替换文本测量逻辑

## 2. `pretext` 是什么

`pretext` 是一个多行文本测量与布局库，核心能力不是“UI 组件”，而是“文本排版计算”。它的 README 里强调了两个主要用法：

- `prepare() + layout()`：先做一次文本分析和测量，再以纯计算方式得到行数和高度
- `prepareWithSegments()` / `layoutWithLines()`：拿到每一行的布局结果，自己控制渲染

它的关键价值是尽量绕开 DOM 测量带来的 reflow 开销，例如 `getBoundingClientRect`、`offsetHeight` 之类的布局测量。[GitHub README](https://github.com/chenglou/pretext)

另外，它还提供了 `rich-inline` 辅助能力，支持：

- code span
- mention
- chip
- 不同字体片段混排
- 行内片段换行控制

这对聊天、富文本卡片、图谱节点标签很有吸引力。[GitHub README](https://github.com/chenglou/pretext)

## 3. 它解决的是什么问题

`pretext` 更适合解决这些问题：

- 长文本在不同宽度下的高度预测
- 不依赖 DOM 的虚拟列表高度估算
- 富文本行内片段的精确换行
- Canvas / SVG / 自绘容器里的文本布局
- 避免文本加载后页面跳动

它不解决这些问题：

- 页面整体视觉设计
- 表单交互
- 普通静态文本展示
- 一般 React 组件布局

所以它不是一个“前端风格升级工具”，而是一个“文本排版性能与精度工具”。

## 4. 对 ToLink 当前代码的适配判断

### 4.1 聊天页面：潜力最大，但现在还不是最佳接入时机

当前聊天详情页见 `src/pages/chats/chat/index.tsx`。

这个页面目前特点很明显：

- 已能读取历史消息
- 发送消息接口还未接通
- 消息渲染还是普通块级文本
- 还没有流式输出、引用卡片、复杂富文本结构

在这个阶段，`pretext` 暂时发挥不出最大价值，因为当前页面还没有“高度不可预估”或“高频重排”的明显压力。

但后续如果你补齐这些能力，它会变得很有价值：

- 流式消息追加时，减少高度抖动
- 长会话虚拟滚动时，提前预测消息高度
- 引用片段、source chip、模型标签做 richer inline layout
- 保持滚动锚点稳定，减少消息到达时的跳屏

结论：

- 长期高适配
- 当前阶段中低优先级

### 4.2 `KnowledgeQA`：如果以后变成真实问答面板，会很适合

当前组件见 `src/components/KnowledgeQA.tsx`。

目前它仍偏静态 demo：

- 消息是固定数据
- 排版主要依赖普通 DOM
- 没有复杂的 inline fragment

但这个组件未来很可能演进成真正的问答主界面，而这是 `pretext` 最可能产生价值的地方之一。

适合的方向包括：

- 回答内容块的高度预估
- 建议问题按钮的平衡换行
- 引用来源标签、文件名 chip、页码 tag 的混排
- 多语言内容的稳定换行

如果将来你要做更接近 ChatGPT / Claude / NotebookLM 风格的回答渲染，这里值得再次评估。

### 4.3 `KnowledgeGraph`：这是最有技术借鉴价值的地方

当前组件见 `src/components/KnowledgeGraph.tsx`。

它现在用 D3 渲染 SVG 节点，节点宽度是这样算的：

- 直接按 `d.label.length * 8 + 12` 估宽

这个方案在中文、英文、混排、宽字符、emoji、不同字重下都不够准确。

这里正好是 `pretext` 的强项，因为它非常适合：

- 在 SVG 节点中精确测文字宽度
- 多语言标签的真实 shrink-wrap
- 节点文本换行，而不是只做单行截断
- 图谱节点尺寸先算好，再喂给 D3 做布局

这一块是我认为当前代码里最值得试点 `pretext` 的场景。

如果只做一个小范围 PoC，我会优先选知识图谱，而不是聊天页。

## 5. 适合接入的具体场景

### 场景 A：图谱节点文本尺寸计算

收益：

- 代替粗糙的 `label.length * 常数`
- 多语言标签宽度更准确
- 节点尺寸、碰撞、布局质量提升明显

成本：

- 中等
- 需要把节点尺寸计算和 D3 布局结合起来

推荐度：

- 很高

### 场景 B：聊天长列表的消息高度预测

收益：

- 后面如果做虚拟列表，会非常有帮助
- 可降低滚动过程中的测量开销
- 更容易做平滑滚动与滚动锚定

成本：

- 较高
- 依赖聊天功能先变复杂

推荐度：

- 中期再做

### 场景 C：引用卡片、chip、mention 的富文本 inline 布局

收益：

- 适合知识问答里的“文件名 + 页码 + 命中片段 + tag”混排
- 可把各种小块组合得更稳定、更可控

成本：

- 中高
- 需要你先明确最终的回答渲染模型

推荐度：

- 中期再做

## 6. 当前不建议引入的原因

### 6.1 当前页面复杂度还不够高

ToLink 现在很多页面还是：

- 常规 DOM 文本
- 固定卡片布局
- 少量静态内容

这类场景用浏览器原生排版就够了，引入 `pretext` 会先增加理解和维护成本。

### 6.2 真实收益要等核心产品能力到位后才显现

例如聊天页真正需要它，通常要满足至少一个条件：

- 消息很多
- 流式输出频繁
- 做虚拟滚动
- 有复杂富文本片段

而你当前聊天页还没有进入这个阶段。

### 6.3 它会引入“文本测量逻辑”和“真实渲染样式同步”的维护要求

README 里特别强调：

- `font` 要和真实 CSS font 同步
- `lineHeight` 要和真实 CSS line-height 同步

这意味着一旦样式改动，你还要同步更新测量配置，否则测量和显示会出现偏差。[GitHub README](https://github.com/chenglou/pretext)

这不是不能接受，但要在收益足够大时再引入。

## 7. 推荐策略

### 策略一：现在不引入，只吸收思路

建议现在先借鉴它的工程思路：

- 把“昂贵预处理”和“高频布局计算”分开
- 避免在滚动和 resize 热路径里反复测 DOM
- 能缓存的文本测量尽量缓存

这是零依赖、低风险、立刻能受益的做法。

### 策略二：先做知识图谱节点 PoC

如果你想尽快验证 `pretext` 是否值得引入，我建议先在 `KnowledgeGraph` 做一个极小试点：

- 只替换节点标签宽度计算
- 不改整体页面结构
- 对比中英文混排节点的尺寸准确性

这是最容易看见收益、也是最不影响主流程的试点方式。

### 策略三：等聊天功能成型后再做正式评估

等以下能力补齐后，再重新评估是否正式引入到聊天系统：

- 消息发送
- 流式返回
- 引用展示
- 长会话历史
- 虚拟列表

到那时，`pretext` 的价值会更容易被放大。

## 8. 建议优先级

### 近期

- 不引入库
- 不增加依赖
- 只记录为候选技术方案

### 中期

- 如果图谱要增强标签布局，优先做 `KnowledgeGraph` 小范围试点

### 后期

- 如果聊天系统升级为长消息、富引用、流式输出、虚拟列表，再考虑正式接入

## 9. 最终结论

`pretext` 对 ToLink 不是“现在就该接”的基础依赖，但它是一个值得保留在技术选型清单里的高质量工具。

对 ToLink 最现实的判断是：

- 它不适合拿来做本轮视觉改版
- 它适合拿来解决未来的文本布局精度和性能问题
- 当前最值得试点的地方是 `KnowledgeGraph`
- 真正最有长期收益的地方是未来的聊天与引用渲染系统
